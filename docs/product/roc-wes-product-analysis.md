# ROC-WES 产品分析报告

> 分析视角：产品（定位 / 用户 / 价值 / 功能 / 竞品 / SWOT / 商业化）
> 分析依据：当前代码库实际实现（`../../src`、`gateway/`、`../../mock`）+ `../../README.md` + `../../package.json`
> 日期：2026-07-31

---

## 0. 一页速览（TL;DR）

ROC-WES 当前**实际**是一个**纯前端、浏览器运行的可视化 SCADA/HMI 组态编辑器 + 只读运行监控视图**，聚焦**仓储自动化（WCS）设备**的可视化与实时数据监控。它用拖拽方式把堆垛机、输送机、AGV、穿梭车、分拣机、提升机、机械手、货架等设备组件摆到画布上，绑定来自 7 种数据源（含真实 Modbus / 西门子 S7 / OPC UA 工业协议，经 Node 网关桥接）的实时数据，并支持数据转换与边沿触发告警。

它的**工程完成度偏高**（协议覆盖广、有演示/真实双模式、有网关监控、领域建模细致），但**产品成熟度仍处原型/内部工具阶段**：无后端、无账号与多用户、无权限、无告警持久化、单向只读监控（无下行控制）、单工程 localStorage 存储、无国际化与主题。

一个突出的产品问题是**定位漂移**：README 宣称的是「企业级仓库执行系统 + 工作流编排 + ECDSA 授权」，但代码里**完全没有**工作流引擎、授权体系，甚至 README 的技术栈与项目结构（仍写作 `roc-mes`）都与现状不符。**名字叫 WES（仓库执行系统），实质是 SCADA/HMI 可视化层**——名实之间存在明显落差。

## 1. 产品定位与价值主张

### 1.1 它实际是什么

剥开命名与文档，从代码反推产品的真实形态：

- **一个「组态画面编辑器」**：用 AntV X6 画布 + 可拖拽设备组件库，搭建一张反映产线/仓库现场的设备布局与监控画面。
- **一个「实时数据可视化运行时」**：编辑好的画面进入 `/run` 只读视图，订阅实时数据、驱动设备组件状态变化与动画，相当于一个 Web 版 HMI（人机界面）。
- **一个「工业协议接入演示框架」**：内置 7 种数据源类型与一套 Node 网关，把浏览器无法直连的原生 TCP 工业协议（Modbus TCP / S7comm / OPC UA）桥接进来，并配套设备仿真器。

### 1.2 名义定位 vs 实际定位

| 维度 | README 名义定位 | 代码实际定位 |
|---|---|---|
| 品类 | 企业级**仓库执行系统（WES）** | Web 可视化 **SCADA/HMI 组态编辑器 + 监控运行时** |
| 核心能力 | 流程图编辑 + **工作流编排** + IoT + 实时数据 + **授权** | 画面组态 + 实时数据绑定 + 工业协议接入 + 告警 |
| 执行/调度 | 暗示有任务编排与执行 | **无**任何调度/执行逻辑，纯监控可视化 |
| 企业特性 | ECDSA 授权、功能权限、节点数限制 | **均不存在**（无相关依赖与代码） |

**价值主张（实际成立的部分）**：让仓储自动化集成商 / 设备工程师**无需安装重型桌面组态软件**，在浏览器里就能快速搭建一张连接真实 PLC/设备的监控画面，并且**开箱即有一套演示模拟数据**用于售前演示与方案验证。

**价值主张（被命名夸大、尚未成立的部分）**：「执行系统（WES）」意味着订单下发、任务调度、与 WMS/WCS 的业务闭环——这些当前完全不具备。当前产品更准确的命名应是「Web 组态/HMI 监控平台（仓储设备方向）」。

## 2. 目标用户与典型场景

### 2.1 画像（基于功能反推）

| 画像 | 诉求 | 当前契合度 |
|---|---|---|
| **仓储自动化集成商 / 售前** | 快速搭一张能连真设备、也能放演示数据的监控大屏，用于投标演示、方案展示 | 高（演示/真实双模式 + 设备组件库正中痛点） |
| **设备/电气工程师** | 把现场 PLC（Modbus/S7/OPC）点位可视化，做状态监视与越限告警 | 中高（协议齐全、有边沿告警；但无历史曲线/告警记录/下控） |
| **产线/仓库运维** | 7×24 实时监控、故障定位、报表 | 低（无后端、无持久化、无多用户、无告警归档，不能常驻生产） |
| **企业 IT / 决策者** | 可纳入现有体系、有权限与审计、可集成 | 低（无账号/权限/审计/集成接口） |

### 2.2 最能成立的场景（甜蜜点）

1. **售前演示 / 方案验证**：演示模式一键起模拟数据，把设备画面"跑起来"给客户看；验证阶段切到真实设备模式连真 PLC。这是当前产品**完成度与价值匹配度最高**的场景。
2. **轻量级设备状态监视看板**：单条线/单台设备的实时状态大屏，工程师本地起服务自用。
3. **教学 / 原型验证**：现代前端栈 + 完整协议链路 + 仿真器，适合作为工业可视化原型或教学样板。

### 2.3 当前撑不起的场景

常驻生产监控、多用户协同、需要下行控制（启停/调速/下发任务）、需要历史数据与报表、需要与 WMS/MES/ERP 集成的执行类场景。

## 3. 功能全景盘点

### 3.1 编辑器（设计态 `/`）

可视化画布（网格/平移/缩放/框选/连线）、撤销重做（20 步）、复制粘贴删除与全套快捷键、JSON 导入导出、极简/图标两种显示模式、手动保存到 localStorage。属性面板分「基础属性 / 数据绑定 / 事件」三页签。

### 3.2 设备组件库（产品的领域护城河）

| 分组 | 组件 | 说明 |
|---|---|---|
| 基础 | 矩形、圆形、卡片节点 | 通用图形/状态卡 |
| **WCS 设备** | 堆垛机、输送机、AGV、穿梭车、分拣机（4 格口）、提升机（多层）、机械手、货架（排×列×层 3D 货位） | 映射真实仓储自动化设备，原始值经 transform 映射为业务状态 |
| IoT 监控 | 仪表盘、实时折线图（ECharts）、指示灯 | 通用监控控件 |

货架组件尤其体现了领域深度：按 `排_列_层` 编址、单/双深位、每货位 empty/occupied/reserved 状态。

### 3.3 数据连接（最宽的能力面）

7 种数据源类型，统一的演示/真实双模式：

| 类型 | 演示（内置 mock） | 真实 | 数据特征 |
|---|---|---|---|
| WebSocket | `ws://localhost:8080/ws` | 用户填地址 | 正弦遥测 |
| HTTP 轮询 | `:8081/api/data` | 用户填地址 | 随机游走 |
| SSE | `:8082/sse` | 用户填地址 | 锯齿斜升 |
| MQTT | `:8083`（WS 桥） | 用户填地址 | 离散档位 |
| 西门子 S7 | `:8084/s7` | 网关 `:19101` + PLC 参数 | 设定值跟踪 |
| OPC UA | `:8085/opc` | 网关 `:19102` + 端点 | 量化阶梯 |
| Modbus | `:8086/modbus` | 网关 `:19100` + 从站参数 | 三角波 |

工业协议链路为「浏览器 → WS → Node 网关 → 原生协议 → PLC」，并各配设备仿真器（19502-19504）。Modbus 支持连续寄存器批量读、S7 支持 rack/slot、OPC UA 支持 NodeId 读取。

### 3.4 数据绑定 / 转换 / 告警

- **绑定**：节点通过 `sourceId` 引用数据源实例 + `pointId` 订阅；
- **转换**：原始值 → 业务状态的 JS 转换函数，以源码字符串持久化、运行时编译（规避 Function 不可序列化）；
- **告警**：节点级事件规则（changed/gt/lt/eq… → console/alert/HTTP），比较类条件采用**上升沿触发**，刻意对齐 PLC 报警语义。

### 3.5 运行态（`/run`）与网关监控

运行态为只读监控视图（不可编辑、仅平移缩放），经 sessionStorage 从编辑器交接，重新绑定全部数据并施加动画。数据源对话框内置**网关/服务监控**：连通性、设备连接状态、数据点实时值、错误告警；演示模式下自动注入样例点位并展示模拟实时数据。

## 4. 技术架构概览（产品视角）

技术栈现代且统一：Vue 3.5 + Vite 8 + TypeScript 6 + Pinia 3 + AntV X6 3 + ECharts 6；工业侧用 nodes7 / node-opcua / modbus-serial / mqtt / aedes / ws。

对产品有约束意义的架构事实：

- **纯前端 + 无后端**：所有持久化在浏览器 localStorage / sessionStorage，无服务端、无数据库。→ 决定了单用户、不可协同、数据不落地、不能常驻。
- **网关是独立 Node 进程**：需手动 `npm run gateway/s7-gateway/opc-gateway` 启动。→ 部署是「前端静态站 + 若干网关进程」，运维形态偏工程化而非产品化。
- **单向数据流**：只有「设备 → 画面」的读取与展示，**没有「画面 → 设备」的下行写/控制通道**。→ 这是「监控」与「控制/执行」的本质分界，也是它无法称为 WES/WCS 的根本原因。

## 5. 竞品与差异化

### 5.1 竞品坐标

| 类别 | 代表 | 特点 | 与 ROC-WES 关系 |
|---|---|---|---|
| 传统桌面 SCADA/组态 | Siemens WinCC、AVEVA InTouch、Rockwell FactoryTalk、组态王、力控 | 重量级、Windows、昂贵、封闭、功能全（含控制/历史/报表） | ROC-WES 想替代其"画面+监控"子集的轻量 Web 化方案 |
| 现代 Web SCADA | Inductive Automation Ignition | Web 化、模块化、含控制/历史/SQL，商业授权 | 最接近的"现代化标杆"，ROC-WES 远未达到其完整度 |
| 流程/ IoT 编排 | Node-RED | 流式编排、偏 IoT 集成而非 HMI 画面 | 理念部分重叠（README 的工作流编排更像 Node-RED 方向，但未实现） |
| IoT 看板 | ThingsBoard、Grafana | 设备接入 + 仪表盘，偏数据看板而非设备布局画面 | ROC-WES 的差异在"设备布局画面"而非"图表看板" |
| 云 IoT 平台 | AWS IoT SiteWise、阿里云 IoT | 云原生、规模化、含孪生 | 不同量级，ROC-WES 是边缘/本地轻量工具 |

### 5.2 差异化机会

- **浏览器原生 + 现代前端栈**：相对传统桌面组态软件，零安装、跨平台、易集成进现有 Web 系统、二次开发友好（MIT 开源）。
- **仓储设备领域组件库**：堆垛机/AGV/穿梭车/货架等开箱即用组件，是相对通用组态/看板工具的**垂直领域壁垒**。
- **演示/真实双模式**：售前演示与真实验证无缝切换，对集成商售前场景非常实用。
- **真实工业协议 + 仿真器齐全**：Modbus/S7/OPC UA 真链路 + 配套仿真，降低了验证门槛。

### 5.3 差异化短板

相对 Ignition / 组态王等成熟产品，缺控制下写、历史库、报表、告警管理、多用户/权限、驱动生态、冗余/高可用——这些恰是工业客户付费的核心。

## 6. SWOT 分析

| | 正面 | 负面 |
|---|---|---|
| **内部** | **S 优势**：现代 Web 栈零安装；仓储设备组件库领域化；7 协议 + 真链路 + 仿真器；演示/真实双模式；转换函数 + 边沿告警贴合工业语义；MIT 开源 | **W 劣势**：无后端/数据库、单用户、无权限；只读监控无下行控制；无历史/报表/告警归档；单工程 localStorage；无 i18n/主题；README 与代码严重脱节；无测试脚本 |
| **外部** | **O 机会**：传统组态软件 Web 化/国产化替代趋势；仓储自动化（AS/RS）行业增长；售前演示与轻量监视的细分空白；开源生态可吸引集成商二次开发 | **T 威胁**：Ignition 等成熟 Web SCADA 下压；云 IoT 平台覆盖；工业客户对稳定性/合规/支持的硬门槛；"组态画面"易被通用低代码/看板工具替代 |

## 7. 关键产品差距与风险

按对产品成立与否的影响排序：

1. **定位/命名漂移（高）**：名为 WES 实为 HMI 监控，README 大量描述（工作流、授权、roc-mes、旧技术栈）与代码不符。对外易造成预期错配与信任损耗。**建议先正名 + 重写 README**。
2. **无下行控制（高）**：只能"看"不能"控"，决定了它进不了生产执行环节，天花板被锁死在"监视/演示"。是否补控制能力，是"工具"与"系统"的分水岭。
3. **无后端与持久化（高）**：单用户、数据不落地、不能常驻、无告警/历史归档，无法支撑运维与生产场景。
4. **无账号/权限/审计（中）**：企业采购的硬门槛，缺失则难以进入正式项目。
5. **工程化短板（中）**：无测试脚本（README 宣称的测试不存在）、无 i18n/主题、网关需手动起进程、无统一部署编排。
6. **告警体系初级（中）**：仅节点级 console/alert/HTTP，无告警中心、确认、分级、归档、推送。

## 8. 商业化与落地可行性

**当前成熟度判断：原型 / 内部工具 / 售前演示级，尚非可交付的企业产品。**

- **可直接变现的形态**：作为**售前演示 / 方案验证工具**与**集成商内部轻量监视工具**，当前完成度已够用，价值真实。
- **要成为"企业级 WES/SCADA 产品"需补齐**（按优先级）：
  1. 后端 + 数据库（工程/画面/数据源/告警/历史的服务化存储）；
  2. 账号 / 权限 / 多用户 / 审计；
  3. 下行控制通道（写点位 + 安全互锁 + 操作审计）——若定位升级为"控制/执行"；
  4. 告警中心 + 历史曲线 + 报表；
  5. 网关的容器化/服务化与统一编排、断线重连与高可用；
  6. i18n、主题、测试体系、CI/CD。
- **更务实的路线**：与其追"大而全的执行系统"，不如**收敛定位为「仓储自动化 Web 组态监控/演示平台」**，把"设备组件库 + 双模式 + 真协议"这一组合做深做透，先吃透集成商售前与轻量监视这一甜蜜点，再决定是否向控制/执行延伸。
